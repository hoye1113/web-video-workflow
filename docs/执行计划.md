## 二、还没解决的四个问题

### 1. 界面：按钮太多，不是给普通人用的

现在是"API 的可视化外壳"：一排按钮（写场景代码 / 抽帧 / 渲染这一镜 / 自动跑导演回路 /
查看编辑代码 / 拼接成片 / 清空）。**剪辑人员不知道该按哪个、按的顺序是什么。**

**FRAMETELL 的做法**：**没有任何操作按钮**。底部一个输入框，
"What would you like to change?"，改什么全靠说话。

### 2. 同一个意象，每一页长得不一样

三页连起来看：页 01 是横向裂缝、页 02 变成纵向、页 03 只剩一条淡压痕。
**页 01 结尾纸已裂开，页 02 开头又变回完好的纸。**

根因：每页的场景代码是模型**独立**写的，提示词只给前一页的**标题**，
没给它**画面长什么样**。

**上游有现成解法**：`window.SCENE_LIBS` —— 项目挂一个共享脚本定义"这个世界"
（那张纸、那道裂缝），每页都调它。`demos/long_scroll/lib/world.js` 就是这么组织的。

### 3. 模型会自作主张画手

页 01 的 note 写了「一只手」，模型就用代码画了一坨深灰色的东西。
PRD 里早写了"手该交给生成图"，但提示词没明说。

### 4. 成本：一页 2 轮回路约 8 分钟

28 页串行 ≈ 4 小时。要么并行，要么减少轮次。

## 三、要做的事（按依赖顺序）

### 阶段 A：把界面重做成聊天驱动

**目标**：普通人打开就知道怎么办 —— 在下面打字，上面自己动。

**✅ 已验证的技术路线（2026-10-15 实跑通过）**

```
浏览器（React + assistant-ui 的 useDataStreamRuntime）
    ↓  POST /api/chat，UI message stream 协议（SSE）
我们的 Python 后端（app/server.py）
    ↓  opencode CLI（走本机凭证，模型写死）
OpenCode Go 套餐的 DeepSeek V4.1 Flash
```

**三个验证结论**：

| # | 结论 | 证据 |
|---|---|---|
| 1 | **`@assistant-ui/react-opencode` 走不通** | ① SDK 等 `opencode server listening` 横幅，桌面版 CLI 打的是 `server listening`；② SDK 的 `setAuthParams` 只在 OpenAPI 声明 security 时才发头，而 opencode 的 `securitySchemes` 是空的 → client 不带鉴权头，而服务要鉴权 |
| 2 | **`useDataStreamRuntime` + 我们自己的后端走通了** | 浏览器里发"现在到哪了？"，收到流式回复，且模型正确读出了项目状态（"02 是渲完又改过代码的，得重渲一遍"） |
| 3 | **后端要按 AI SDK 的 UI message stream 吐** | 响应头 `x-vercel-ai-ui-message-stream: v1` + `data: {...}` 行 + `data: [DONE]`。实现见 `app/chat.py`，几十行 |

**两个踩到就记下的细节**：
- 请求体**不是** `{message: "..."}`，是 AI SDK 的整个线程 `{messages: [{role, parts:[{type:"text",text}]}]}`（旧版是 `content`）。后端两种都要认（已实现 `_last_user_text`）。
- `useDataStreamRuntime` 有 **`onData` 回调**，专门收 `data-*` 自定义部件 —— **这就是"聊天驱动面板"的钩子**。后端发 `data: {"type":"data-actions","data":{"actions":[...]}}`，前端 onData 收到就去刷新对应面板。

**模型写死**：`app/llm.py` 里的 `MODEL = "opencode-go/deepseek-v4.1-flash"`，
**不给界面切 provider / 切模型**（绑定 OpenCode Go 套餐，没有别的凭证可用）。

**技术选型**

| 要什么 | 用哪个 | 备注 |
|---|---|---|
| 聊天界面 + 运行时 | **`@assistant-ui/react` + `@assistant-ui/react-data-stream`** | ✅ 已验证能接我们的后端 |
| 三栏可拖拽布局 | **`bvaughn/react-resizable-panels`** | 社区标准。**不要用 shadcn 的 Resizable wrapper**，它和 v4 不兼容 |
| 基础组件 | shadcn/ui | assistant-ui 本身就建在它上面 |
| 构建 | **Vite + React + TS** | 已验证（`experiments/aui-test`） |
| ~~`@assistant-ui/react-opencode`~~ | ❌ 不用 | 见上面结论 1 |

**界面形状（照 FRAMETELL）**

```
┌──────────────────────────────────────────────────────────────┐
│  项目名                                    [导出] [设置]        │
├───────────────┬──────────────────────────────────────────────┤
│               │                                              │
│  页面列表      │           连续预览（引擎实时渲染）             │
│  （带缩略图    │                                              │
│    和状态点）   │                                              │
│               │                                              │
│  01 ● 钩子     │                                              │
│  02 ● 钩子     ├──────────────────────────────────────────────┤
│  03 ○ 案例一   │  任务：正在渲第 12 页 ▓▓▓▓░░ 62%              │
│  …            │                                              │
├───────────────┴──────────────────────────────────────────────┤
│  ┌────────────────────────────────────────────────────────┐  │

│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

**关键：操作入口只有聊天框。** 页面列表和预览是**只读的状态显示**，不是操作面板。

**聊天怎么驱动界面**

模型回话时顺带输出一个 JSON，后端把它变成 `data-actions` 部件，
前端的 `onData` 收到就执行对应动作并刷新面板：

| 操作 | 干什么 | 界面反应 |
|---|---|---|
| `list_pages` | 列页面和状态 | 刷新左栏 |
| `write_scene(shot)` | 写这一页的场景代码 | 中栏预览刷新，左栏状态点变色 |
| `render_shot(shot)` | 渲这一页 | 任务条出现进度 |
| `review_shot(shot)` | 抽帧 + 评审 | 聊天里出评审卡（打分 + 问题 + 改法） |
| `render_film` | 全部渲完并拼接 | 出成片播放器 |

这样"把第 02 页的裂缝画细一点"这句话，模型拆成
`write_scene("02")` → `render_shot("02")` → `review_shot("02")`，界面全程自己动。

**后端要补的**：
- ✅ `/api/chat`（SSE，UI message stream 协议）—— 已实现并验证
- ⬜ **任务进度也走推送**（现在前端轮询 `/api/jobs`），改成 SSE
- ⬜ 把上面五个操作从"返回 job id"改成"能被 chat 的 actions 调起"

**做完的验收**：拿 01-03 页走一遍，**全程只用打字**，不点任何操作按钮。

### 阶段 B：共享世界（修"每页一个样子"）

## 五、协议备忘（接的时候别踩）

**我们后端吐给前端的**（UI message stream，`app/chat.py` 已实现）：

```
HTTP/1.1 200 OK
Content-Type: text/event-stream; charset=utf-8
x-vercel-ai-ui-message-stream: v1        ← 前端靠这个头识别协议

data: {"type":"start"}

data: {"type":"data-status","data":{"text":"模型在想…"}}      ← 自定义部件，onData 收
data: {"type":"text-delta","id":"t0","delta":"要说的话"}
data: {"type":"data-actions","data":{"actions":[{"op":"write_scene","shot":"02"}]}}
data: {"type":"finish"}

data: [DONE]
```

**前端发给我们的**（AI SDK 的线程形状，不是 `{message}`）：

```json
{"project": "marriage_full",
 "messages": [{"role":"user","parts":[{"type":"text","text":"现在到哪了？"}]}]}
```

旧版可能是 `content` 而不是 `parts`，两种都要认（`_last_user_text` 已处理）。

## 八、风险与前提

- ~~`@assistant-ui/react-opencode` 是实验性的~~ → **已验证不适用，不用了。**
- `useDataStreamRuntime` 的那个包也在快速迭代，但协议（AI SDK 的）是稳定的。
- 本机 opencode 服务会跟着桌面版重启一起死（踩过）。**中转在后端，后端有探活重建**
  （`llm._ensure` 每次调用前都检查），所以前端不受影响。
- 转写模型（faster-whisper）第一次用要从 HuggingFace 下，**必须走系统代理**
  （`127.0.0.1:17890`），脚本已经自动读。
- **Python 后端要能长跑**（SSE 长连接）。现在是 `ThreadingHTTPServer`，够用，
  但要注意线程数。
